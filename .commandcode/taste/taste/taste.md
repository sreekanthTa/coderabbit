# Taste
- Prefers an incremental, gate-based workflow: inspect the project and propose a plan (e.g. folder structure) with explanations first, then wait for explicit approval before implementing code. Confidence: 0.9
- Explicitly asks the assistant to stop and "wait for further instructions before implementing" — does not want code written ahead of his go-ahead. Confidence: 0.85
- Wants minimal file creation up front ("do not create lots of files yet"); prefers to review the proposed structure before anything is scaffolded — but once he says "just scaffold", expects the files to actually be created, not merely proposed. Confidence: 0.8
- Strongly anti-over-engineering: explicitly rules out premature complexity and future features in early versions (no RAG, no LangGraph, no Redis, no database, no React, no deployment/AWS, no multi-agent architecture). Confidence: 0.9
- Labels work by version (V1, etc.) and scopes features strictly to that version's requirements. Confidence: 0.75
- Backend stack is a swappable implementation detail, not a fixed commitment — started with Node.js + TypeScript + Express (Octokit, GitHub App + Webhooks), then pivoted to Python + FastAPI. Confidence: 0.7
- When leaning Python for a backend/API service, prefers FastAPI with pydantic-settings for config, PyGithub for GitHub App auth, and an OpenAI-compatible LLM client. Confidence: 0.6
- For Python projects, wants them initialized and managed with `uv` (pyproject.toml-based), explicitly requesting `uv init` over requirements.txt/pip workflows. Confidence: 0.7
- Strongly DRY: insists shared logic live in one reusable function/service that multiple callers invoke (e.g. both `/review` and `/webhooks/github` calling a single `review_pull_request`), rather than duplicating the same flow in each entrypoint. Confidence: 0.8
- Prefers modular code organization over monoliths: asks for large single files to be split by responsibility into proper folders (e.g. `routes/`, `services/`, `config.py`, `schemas.py`) with a thin entrypoint. Confidence: 0.75
- For LLM-backed features, prefers structured, typed outputs driven by explicitly declared Pydantic models (e.g. `ReviewIssue`/`CodeReview` with `list[...]` fields, wired through LangChain `with_structured_output`) instead of returning free-text strings. Confidence: 0.6
- Wants his own library/implementation choices preserved — pushes back when the assistant swaps his chosen dependency (e.g. `langchain_groq`/`ChatGroq`) for a "recommended" simpler alternative; the assistant should honor the existing code and flag trade-offs instead of silently replacing them. Confidence: 0.7
- Reports problems by pasting the raw artifact verbatim — terminal session / error transcript (command output, HTTP status, traceback), or a full dump of the page/UI where the bug is visible (e.g. the whole GitHub PR conversation) — rather than describing the issue in prose; expects the assistant to read the pasted output and diagnose the root cause itself. Confidence: 0.7

- Communicates in short, informal, typo-laden messages (often paired with an IDE selection of the offending lines) and expects the assistant to diagnose the actual root cause rather than answer the literal phrasing. Confidence: 0.55
